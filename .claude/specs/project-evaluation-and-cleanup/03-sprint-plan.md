## 详细User Story

### EVAL-001: 代码使用分析
**Epic**: 项目评估与分析
**点数**: 8
**优先级**: 高
**Sprint**: Sprint 1

**User Story**:
作为技术负责人，我想了解哪些代码文件是活跃使用的，哪些是冗余的，以便做出明智的清理决策。

**验收标准**:
- [ ] 系统能扫描所有源代码文件（.sh, .py, .yaml, .md等）
- [ ] 识别未被引用的脚本文件（通过静态分析和Git历史）
- [ ] 识别未被使用的配置文件（通过实际部署流程验证）
- [ ] 生成文件使用频率报告（基于Git commit历史）
- [ ] 标记超过6个月未修改的文件
- [ ] 输出格式为Markdown表格，包含文件路径、最后修改时间、引用次数

**技术实现**:
- 创建`tools/evaluation/analyze_code.sh`脚本
- 使用Git log分析文件修改历史
- 使用grep分析source和import语句
- 输出到`docs/evaluation/code_usage_report.md`

**任务分解**:
1. 设计代码分析算法和数据结构（4h）
2. 实现Git历史分析功能（6h）
3. 实现静态引用分析（8h）
4. 生成Markdown报告（4h）
5. 编写单元测试（4h）
6. 代码审查和文档（2h）

**Definition of Done**:
- [ ] 代码完成并遵循项目规范（shellcheck通过）
- [ ] 单元测试编写并通过
- [ ] 代码审查通过
- [ ] 能够识别至少80%的冗余文件
- [ ] 文档更新（README, CHANGELOG）
- [ ] 在测试环境验证通过

## 会议与仪式

### Sprint Planning（每个Sprint开始）
- **时长**: 4小时
- **参与者**: 全体团队
- **议程**:
  - 回顾上个Sprint成果
  - 讲解本Sprint目标和User Story
  - 任务分解和认领
  - 识别风险和依赖

### Daily Standup（每日）
- **时长**: 15分钟
- **参与者**: 全体团队
- **议程**:
  - 昨天完成了什么
  - 今天计划做什么
  - 有什么阻碍

### Sprint Review（每个Sprint结束）
- **时长**: 2小时
- **参与者**: 全体团队 + 利益相关方
- **议程**:
  - 演示本Sprint交付物
  - 收集反馈
  - 更新Product Backlog

### Sprint Retrospective（每个Sprint结束）
- **时长**: 1.5小时
- **参与者**: 全体团队
- **议程**:
  - 什么做得好
  - 什么需要改进
  - 下个Sprint的改进行动
